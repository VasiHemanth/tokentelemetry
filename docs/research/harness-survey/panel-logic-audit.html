01 — THE CONTRADICTION

Two claims, same page, same second

The Claude Code panel puts these side by side. Both are read from disk at request time, so they describe the same instant.

Background jobs · jobs/<id>/state.json 1 min ago Most recent Claude session TokenTelemetry holds. Six jobs marked LIVE, the newest updated 11 minutes ago. The agent is unambiguously talking to the API right now.
cannot
both
Subscription usage · cachedUsageUtilization 94.9 h ago Age of the quota reading. Both windows it describes have since closed — the 5-hour one 91 hours ago, the 7-day one 23 hours ago.

The intuition that these can't both be right is correct, and it points at a real thing. The resolution is not what you'd expect.

The file is fresh. The field is not.

~/.claude.json was last written 11 minutes ago. Inside it, cachedUsageUtilization.fetchedAtMs is 94.9 hours old. Claude Code is actively writing that file and deliberately not refreshing that block.

So the quota is not stale because the agent is idle. It is stale because ordinary API traffic does not refresh it — the block is written only when something explicitly asks the server for usage. A panel that reads it gets whatever the last such request returned, however long ago that was.

That makes the current display honest but nearly useless: it greys the meters and says the figure is stale, which is true, and then offers no number that isn't. For a subscription account it can't even offer a denominator — limit_dollars, used_dollars and remaining_dollars are all null, so the $X of $Y used line the code builds never renders for this account at all.

02 — THE MODEL

Freshness has two axes, and the code only checks one

The current test is resets_at < now — has the window ended. That collapses two independent questions into one, and the collapse is where the real bug hides.

window open · reading fresh Trustworthy Show it plainly. The number describes a window still running, and it was read recently enough to still be roughly true.
window open · reading old The dangerous one Renders with a live countdown and no warning, because the window really is open. Nothing in the current code can catch this. Grok sits here.
window closed · reading fresh History A complete, final record of a window that ended. Worth keeping as a past-period figure, not as status.
window closed · reading old Caught today Greyed and labelled stale. Claude sits here — and the current one-axis test happens to get it right, for the wrong reason.

columns: reading age  ·  rows: window state

The proposed rule replaces "has the window ended" with a ratio: a reading is current when its age is small relative to the window it describes. Forty-four hours into a seven-day window means a quarter of that window went unobserved, whether or not the window is still open.

03 — THE SAME DISEASE, EVERYWHERE

“Active 26 days ago” is measuring a file, not you

Every panel header renders active {time} ago. A reader takes that to mean "when I last used this agent". It doesn't mean that consistently — for some agents it's a config file's mtime, for others a log write, for others a real session. 04 — THE FIX WE ALREADY OWN

TokenTelemetry can measure the window itself

The reason the quota card has nothing fresh to fall back on is that it only ever looks at the agent's cache. But the rolling windows are computable from session data already held — every session carries a timestamp and a token count, which is all a 5-hour or 7-day window needs.

What this can and cannot replace

It gives observed usage in the window, always current. It cannot give percent of subscription limit — the limit fields come back null for subscription accounts, so no local computation can recover the denominator.

So the card becomes two rows rather than one: the official percentage stamped with its age, and beneath it the measured consumption that is always true. When the official figure is hours old, the measured row is the one carrying the information.

06 — DISK FOOTPRINT

The tooltip should answer “can I delete this?”

Today hovering a segment yields a native browser tooltip reading snapshot — 38.3 MB. That restates the legend directly beneath it. The label and the size are the two things already on screen; the tooltip spends its one moment of attention repeating them.

Nobody hovers a disk chart to learn a filename. They hover it because something is large and they want to know what it is, whether it will come back, and what breaks if it goes. Hover a segment below.

Keyboard: tab to a segment. The card holds the last segment you touched rather than emptying on mouse-out, so it can be read.

What changed, and why each part earns its space

  • A classification, not a name. Primary data / Rebuildable / Transient is the first thing a person needs, and it is derivable from the part label the backend already emits.
  • The consequence, stated plainly. "Deleting this loses your edit history" and "this rebuilds on next run" are different answers, and the difference is the entire reason someone opened the tooltip.
  • Two denominators. A segment's share of its agent says whether it dominates that agent; its share of the 20.86 GB fleet says whether it's worth your attention at all. 38.3 MB is half of OpenCode and 0.2% of the fleet — both facts matter, and neither is on screen today.
  • One stat call short. The one thing a person also wants is when this was last written — a cache untouched for three months is a different proposition from one written this morning. The backend already walks these directories; carrying the max mtime out of that walk costs nothing extra.

The same card shape works for every agent, because the classification comes from the part label rather than from bespoke per-agent copy. Roughly forty distinct labels appear across the fleet and they fall into a handful of buckets.
