## Confirmed findings

### 1. CRITICAL — Saving power settings silently reprices every unpriced cloud model as local electricity

**File:** `backend/pricing.py:671-685`, guarded by `backend/power_config.py:142-167`,
triggered from `frontend/src/components/settings/PowerSettings.tsx:49-58`

When `calculate_cost` finds no API rate for a model, it checks
`local_power_enabled()` and, if true, returns `electricity_cost(output_tokens, ...)`
instead of the `_default` per-token rate. `local_power_enabled()` returns true
whenever `power.json` holds an in-range `loadWatts`/`costPerKwh`.

The power settings form always submits those two fields, hydrated from the
server's *effective* config. `loadWatts` there is not the flat
`DEFAULT_LOAD_WATTS = 80` — `load_power_config` fills it from chip-aware
detection for the machine (hence the `22` in the trace below). So a user who
opens the page only to add a subscription endpoint, and never touches the power
inputs, still round-trips a machine-detected wattage into a persisted opt-in on
save. From then on every model missing from the pricing tables is costed as if
it had run on the user's own hardware.

`electricity_cost` is passed only `output_tokens`, so input tokens cost exactly
$0.00 regardless of volume.

Reproduced end to end (fresh HOME, simulating the save described above):

```
BEFORE any settings save (no power.json):
   1M in + 1M out = $12.00

power.json now on disk: {"loadWatts": 22, "costPerKwh": 0.15,
                         "localEndpoints": [], "subscriptionEndpoints": ["https://api.example.com"]}
local_power_enabled() -> True

AFTER that save:
   1M in + 1M out = $0.0306
   1M in  only    = $0.0000
```

A ~392x under-report of real API spend, with `localEndpoints` empty — the user
runs nothing locally. The docstring at `power_config.py:143-151` shows this hazard
was anticipated for the `subscriptionEndpoints` case and that requiring an explicit
power figure was believed to fix it; the UI supplies that power figure
unconditionally, which defeats the guard.

**Why it matters beyond the unpriced tail:** 397 `by_provider` rows and 173
`pricing` rows were removed from `pricing_data.json` in this range, so the set of
models that reach this fallback is not static.

**Suggested direction (not applied — fixes are separate, human-initiated work):**
distinguish "user deliberately opted into electricity pricing" from "the form
echoed back a default", e.g. an explicit `localPricingEnabled` flag, or omit
power fields from the save payload when untouched.

Filed as issue #341.

### 2. HIGH — Hermes rollup drops known tokens when the paired column is NULL

**File:** `backend/harness_panels/hermes.py:70`

The provider rollup sums tokens with `SUM(input_tokens + output_tokens)`. In
SQLite `NULL + anything` is `NULL`, and `SUM` skips NULLs, so a row where one
side is recorded and the other is NULL contributes nothing — the known component
is discarded rather than counted.

Reproduced:

```python
c.executemany('INSERT INTO t VALUES (?,?,?)', [(100, None, None), (50, 25, 1.5)])
c.execute('SELECT SUM(input_tokens + output_tokens) FROM t').fetchone()[0]
# -> 75 ; the truth is 175. The 100 known input tokens vanish.
```

This is an omission rather than a deliberate choice: the same SELECT statement
three lines below handles the identical hazard correctly with
`SUM(COALESCE(actual_cost_usd, 0))`.

Two neighbouring absent-vs-zero conflations share the root cause and were
confirmed at the SQL level, though they are a presentation judgment rather than
data loss — `hermes.py:73` turns an unrecorded `actual_cost_usd` into `$0.00`,
and `copilot.py:52` counts a row with NULL `total_nano_aiu` as a request
contributing zero billed amount.

Filed as issue #342.

### 3-7. `backend/quotas.py` — five high-severity findings, all reproduced

`backend/quotas.py` is 1,441 lines, net-new in this range and never previously
audited. A deep audit of it was run in the resumed session once quota was
available. Seven of its eight findings were reproduced with throwaway scripts
rather than argued from inspection; three were additionally spot-verified by
hand while writing this report.

The unifying theme is worth stating once, because it is the same defect wearing
five different outfits: **the quota surfaces present unknown, stale, or
someone-else's data as a confident current number, and the one direction the
gauge errs in is "you're fine."** A gauge that exists to answer "am I about to
be cut off?" answers "no" most confidently exactly when it has no data.

| # | File | Defect | Issue |
|---|---|---|---|
| 3 | `quotas.py:1366` | Snapshots are never pruned, so a signed-out provider renders a month-old percentage as live — and `harness_panels/base.py:505` captions it "live from the provider" | #344 |
| 4 | `quotas.py:1329` | Freshness check has no upper bound; a future `fetchedAt` freezes all refreshes for ~172 days while reporting `stale: false` | #345 |
| 5 | `quotas.py:1314` | Cache-lock timeout returns empty `capabilities` *and* empty `errors`, so the Plan-limits control vanishes rather than reporting a failure | #346 |
| 6 | `quotas.py:1027` | Grok substitutes `0` for a missing `creditUsagePercent`, showing a full green bar at 0% when credits may be exhausted | #347 |
| 7 | `quotas.py:922` | Cursor's `or` fallback treats a genuine `0.0` as absent, attributing the whole team pool's spend to an individual | #348 |

Three of these were verified independently while writing this report:

- **The `stale` flag is dead.** `QuotaSnapshot.wire` computes it, and grep across
  every consumer returns exactly one hit — `frontend/src/lib/quotas.ts:22`, the
  type declaration. It is referenced nowhere else, in either the frontend or the
  menubar.
- **Grok's zero is an internal inconsistency, not a convention.** `_window_resource`
  (`quotas.py:446-447`) returns `None` when `used_percent` is absent, and Claude
  and OpenCode do the same. Grok alone fabricates a zero.
- **Cursor's `or` chain** reads exactly as reported at `quotas.py:922-924`.

Two further findings are medium and recorded here only: `quotas.py:1379` writes a
`SCHEMA` string into every cache file and never checks it on read, so a
future-format file is parsed as v1; and `quotas.py:792` raises `TypeError` on a
Copilot entitlement with no `remaining`, discarding two sibling entries that
parsed fine and reporting a network failure when GitHub actually answered 200.

One finding was returned appropriately hedged and is **not** treated as a live
bug: `quotas.py:471` derives Codex window keys from their measured duration with
no collision check. The auditing agent stated plainly that it had no evidence any
current plan emits a colliding shape, so this is a robustness gap in how the key
is derived rather than an observed misreading. Recorded, not filed.

## Refuted candidates

### `pricing_data.json` deletions do not zero out known models — REFUTED

The headline risk going in was that the 5,149-line deletion in
`backend/pricing_data.json` had dropped rows that lookup code still references,
falling through to $0. Checked directly rather than by inspection:

- Both maps grew net: `by_provider` 5,291 → 5,831, `pricing` 2,436 → 2,589.
- 397 `by_provider` and 173 `pricing` keys were nonetheless removed, including
  real ones users have history for: `anthropic|claude-opus-4-1`,
  `anthropic|claude-opus-4-1-20250805`, `anthropic/claude-3-7-sonnet`,
  `gemini-2.0-flash-001`, `gpt-3.5-turbo-0613`, `deepseek-v3.1`.
- Probing the real lookup, `claude-opus-4-1-20250805` still prices at $90.00 per
  1M in + 1M out, matching Opus 4.1's $15/$75. The curated inline tables and the
  fuzzy prefix matcher absorb the removals.

The removals are safe on their own. They matter only as input to finding 1, which
is what actually turns an unpriced model into a near-zero number.
