### 1. CRITICAL — Saving power settings silently reprices every unpriced cloud model as local electricity

**File:** `backend/pricing.py:671-685`, guarded by `backend/power_config.py:142-167`,
triggered from `frontend/src/components/settings/PowerSettings.tsx:49-58`

When `calculate_cost` finds no API rate for a model, it checks
`local_power_enabled()` and, if true, returns `electricity_cost(output_tokens, ...)`
instead of the `_default` per-token rate. `local_power_enabled()` returns true
whenever `power.json` holds an in-range `loadWatts`/`costPerKwh`.

The power settings form always submits those two fields, hydrated from the
server's *effective* config. `loadWatts` there is not the flat
`DEFAULT_LOAD_WATTS = 80` — `load_power_config` fills it from chip-aware
detection for the machine (hence the `22` in the trace below). So a user who
opens the page only to add a subscription endpoint, and never touches the power
inputs, still round-trips a machine-detected wattage into a persisted opt-in on
save. From then on every model missing from the pricing tables is costed as if
it had run on the user's own hardware.

`electricity_cost` is passed only `output_tokens`, so input tokens cost exactly
$0.00 regardless of volume.

Reproduced end to end (fresh HOME, simulating the save described above):

```
BEFORE any settings save (no power.json):
   1M in + 1M out = $12.00

power.json now on disk: {"loadWatts": 22, "costPerKwh": 0.15,
                         "localEndpoints": [], "subscriptionEndpoints": ["https://api.example.com"]}
local_power_enabled() -> True

AFTER that save:
   1M in + 1M out = $0.0306
   1M in  only    = $0.0000
```

A ~392x under-report of real API spend, with `localEndpoints` empty — the user
runs nothing locally. The docstring at `power_config.py:143-151` shows this hazard
was anticipated for the `subscriptionEndpoints` case and that requiring an explicit
power figure was believed to fix it; the UI supplies that power figure
unconditionally, which defeats the guard.

**Why it matters beyond the unpriced tail:** 397 `by_provider` rows and 173
`pricing` rows were removed from `pricing_data.json` in this range, so the set of
models that reach this fallback is not static.

**Suggested direction (not applied — fixes are separate, human-initiated work):**
distinguish "user deliberately opted into electricity pricing" from "the form
echoed back a default", e.g. an explicit `localPricingEnabled` flag, or omit
power fields from the save payload when untouched.

Filed as issue #341.

### 2. HIGH — Hermes rollup drops known tokens when the paired column is NULL

**File:** `backend/harness_panels/hermes.py:70`

The provider rollup sums tokens with `SUM(input_tokens + output_tokens)`. In
SQLite `NULL + anything` is `NULL`, and `SUM` skips NULLs, so a row where one
side is recorded and the other is NULL contributes nothing — the known component
is discarded rather than counted.

Reproduced:

```python
c.executemany('INSERT INTO t VALUES (?,?,?)', [(100, None, None), (50, 25, 1.5)])
c.execute('SELECT SUM(input_tokens + output_tokens) FROM t').fetchone()[0]
# -> 75 ; the truth is 175. The 100 known input tokens vanish.
```

This is an omission rather than a deliberate choice: the same SELECT statement
three lines below handles the identical hazard correctly with
`SUM(COALESCE(actual_cost_usd, 0))`.

Two neighbouring absent-vs-zero conflations share the root cause and were
confirmed at the SQL level, though they are a presentation judgment rather than
data loss — `hermes.py:73` turns an unrecorded `actual_cost_usd` into `$0.00`,
and `copilot.py:52` counts a row with NULL `total_nano_aiu` as a request
contributing zero billed amount.

Filed as issue #342.

### 8. CRITICAL — `/analytics` merges zero-token stubs over durable history

**File:** `backend/main.py:11152` · Issue #349

**This is the headline finding of the audit.** It is the PR #131 bug class — a
stub row crushing real persisted data — recurring on the *read* path this time
rather than the write path, which is exactly why the write-path fix did not
prevent it.

The write path is guarded: `history_store.upsert_sessions` protects stubs at
`backend/history_store.py:219-224`, where a stub's `DO UPDATE SET` touches only
liveness columns. The read path has no such guard. In `get_analytics`, `merged`
is seeded from `history_store.query()` and then every live session that passes
`_session_in_filters` overwrites its key — and `_session_in_filters`
(`backend/main.py:11099`) never looks at `stub`.

The sequence needs no user error. A transcript is pruned by Claude Code's own
`cleanupPeriodDays` pass, but `~/.claude/history.jsonl` still carries the
`sessionId`; the next scan therefore manufactures a `stub: True` session with
zero tokens (`backend/main.py:6572-6581`), and nothing later clears the flag
because `backend/main.py:7018` sits inside `if session_file:`.

Crucially the row does **not** disappear — `session_count` still reports 1 — so
the UI shows "1 session, 0 tokens, $0.00" rather than a gap. That is why this has
gone unnoticed. And it is permanent rather than transient: `history.jsonl`
outlives the transcripts, so every pruned session is re-stubbed on every scan,
forever.

**Measured production impact.** Taken read-only from the maintainer's own machine
by the auditing agent, then **independently recomputed by a separate script during
report review**. Every figure reproduced exactly:

```
distinct sessionId in history.jsonl : 197
orphaned (no transcript on disk)    : 166
claude rows in store TOTAL          : 83,043,562 tokens  $6,748.49
orphaned sids WITH a real store row : 80
  their tokens                      : 54,437,385
  their cost                        : $4,673.23
  share of claude cost at risk      : 69.2%
```

69% of the durable Claude history on this machine is being zeroed on every
`/analytics` request today.

### 9. HIGH — Codex partial parse marked complete, blind-replaces the durable row

**File:** `backend/main.py:7264` · Issue #350

A read/parse error on one of a Codex session's rollout files is swallowed
per-file, yet the truncated result is still marked `stub=False`, cached as
authoritative, and blind-replaced into history. Reproduced at a **98.75% loss**
(1,200,000 tokens → 15,000) by making the newer of two rollout files unreadable.

The root gap is architectural: a scanner has no way to say "this parse was
incomplete". `stub` is the only signal and a mid-file abort never sets it. Note
that a `MAX()` conflict clause is *not* the fix — CACHE_VERSION 11's dedupe fix
legitimately lowered totals, so a monotonic guard would have blocked a correct
repair.

### 10. HIGH — `scan_cache` pins a stale parse on non-monotonic mtime

**File:** `backend/scan_cache.py:117` · Issue #351

`read_cache` accepts `cached_mtime >= source_mtime`, so a session parsed while the
mtime source ran ahead (NAS/SMB clock skew, an NTP step-back) freezes at that
moment's tokens forever, and — because a cache hit sets `stub=False` — the frozen
undercount is written through the non-stub conflict clause on every scan.
Reproduced: 140,000 appended tokens invisible to both UI and store for a full day.

The equality case needs no clock anomaly at all: on a coarse-resolution filesystem
(exFAT at 2s, many SMB mounts at 1s) turns appended inside the same tick as the
parse are lost permanently if the session then goes idle. The module docstring
claims the in-payload `_mtime` makes this "deterministic under coarse filesystem
mtime resolution", which is backwards — coarse resolution is precisely what `>=`
cannot survive.

### 11. HIGH — A failed summarization re-stamps the stale narrative as fresh

**File:** `backend/main.py:12098-12105` · Issue #352

When summarization fails after a transcript has grown, the code falls back to the
cached narrative — reasonable on its own — but then stores it under the **new**
`content_hash`. That is what makes the failure permanent: every later request sees
`cached.content_hash == chash`, reports `stale: False`, and never regenerates.

A session summarized at 3 events, grown to 10, then re-summarized while the
backend is down, will show the 3-event narrative as the summary of the 10-event
trace forever. Proven by driving `backend/summaries.py` directly: after a
simulated generation failure on a grown trace, the stored hash equalled the new
hash while the narrative was still the old one, and it was treated as fresh.

The sharp edge is that the one signal which would trigger a retry is precisely
what the failure path overwrites.

### 12. HIGH — `/dsh/lifecycle` summarises the capped tail as if it were the whole

**File:** `backend/main.py:5337` and `backend/main.py:5395-5400` · Issue #353

`_dsh_lifecycle_events` returns `out[-limit:]`, and the endpoint then computes
`**_dsh_lifecycle_summary(events)` over that already-truncated list. No field in
the response reports the true total.

This is the same shape as PR #131 — a cap applied before an aggregate — and the
direction of the error matters: the slice keeps the *tail*, so a plugin whose
failures are historical under-reports exactly the failures a user is looking for.
Proven against a synthetic 600-line log: true `{'transitions': 600, 'failed': 550}`
vs `{'transitions': 500, 'failed': 450}` at the endpoint's default `limit=500`.

Worth noting that the convention already exists elsewhere in this codebase —
`/hermes/sessions` returns `pagination.total`, grok-forensics returns `counts`,
`HermesSessionExplorer` has `cappedOut` messaging. This endpoint simply doesn't
follow it.

### 13. Trust boundaries — reported privately, not in this file

The trust-boundary sweep found a path-traversal-class defect that results in file
contents being returned through the API. Because this repository is public and
the defect is unpatched, **the details are deliberately not written here.** They
are in a private draft security advisory: `GHSA-3w4h-37hx-9348`.

Three related lower-severity instances of the same root cause (one high, two
medium) are recorded in that advisory as well, so the whole cluster can be fixed
and disclosed together.

What can be said publicly without aiding anyone: the root cause is that ids read
off disk, and one URL path parameter, reach filesystem joins without the
validation this codebase already applies to the same class of input elsewhere
(`backend/scan_cache.py:60`, `_require_safe_component`). The pattern is duplicated
across roughly fifteen agent-specific branches, so a single normalize-and-reject
helper at the boundary is a more durable fix than patching each join.

This section should be expanded with the specifics once the advisory is published.

### Breadth-wave mediums (recorded, not filed)

**Timestamp / timezone**

- `backend/main.py:7172` — the Codex per-session daily breakdown keys buckets with
  `_aware(event_dt).strftime("%Y-%m-%d")`, forcing UTC, while this same file's
  `_bucket_key` (`main.py:11065`) documents itself as *"Local-time bucket label…
  Always local"* and uses `ts.astimezone()`. Codex events between 00:00–05:30 IST
  therefore land in the previous local day. Proven: `2026-09-09T20:00:00Z` gives
  `2026-09-09` under `_aware()` and `2026-09-10` under the local idiom. Medium
  rather than high because the visible consequence is narrow — that day key feeds
  the `at=` date for repricing-banded models, so a session straddling a price
  change can be priced at the wrong day's rate.
- `backend/main.py:2264-2266` — Hermes cron `next_run_at`/`last_run_at` are parsed
  naive-defaults-to-UTC, although this repo's own `hermes_telemetry.py`
  (`parse_log_ts`) documents that Hermes writes naive timestamps representing
  *local* wall clock. For an IST user that shifts at-risk schedule detection by the
  full UTC offset on the Hermes Schedules page.

**Silent caps**

- `backend/hermes_telemetry.py:559,564-567` — `_tools()` caps `top_by_calls` and
  `top_by_failure_rate` at 10 but, unlike the sibling `_outcomes()` in the same
  file (which emits `models_total` precisely so the UI can say "Top N of M"),
  reports no `tools_total`. The Hermes Tools card therefore shows 10 of 40 tools
  with no caption, while the adjacent Models breakdown does have one. A tool with
  a genuinely high failure rate that misses the top 10 is indistinguishable from
  one that doesn't exist.

**Persisted state**

- `backend/main.py:8422-8444` — the "already archived" guard reads
  `s.get("transcript_archived")` from a freshly-parsed scan dict, and no parser
  ever sets that key (only `history_store`'s row-to-dict does, at
  `history_store.py:330`, which is never merged back onto scan output). So the skip
  never fires and every ~30s scan re-reads the transcript and overwrites the
  durable archive unconditionally. A read landing mid-write of a live session can
  replace a complete blob with a truncated one, and there is no size or timestamp
  comparison to prevent a worse capture replacing a better one.
- `backend/main.py:955-993` — the Antigravity token cache is validated only by
  `cache_file.stat().st_mtime >= tf.stat().st_mtime`, with no cache version and no
  record of which transcript backed the cached value. Once the richer
  `transcript_full.jsonl` appears alongside a cache written from `transcript.jsonl`,
  an equal-or-older mtime pins the short-transcript figures permanently. Same `>=`
  hazard as #351, in a second place. The write is also a direct `json.dump` with no
  tmp+rename.
- `backend/summaries.py:410-423` — `save_config()` uses a plain in-place
  `write_text`, while `harness_config.py`, `power_config.py`, `billing_mode.py` and
  `agent_retention.py` all use tempfile + `os.replace` specifically so "a crash
  mid-write won't corrupt config" (per `harness_config.py`'s own docstring). A
  crash mid-flush truncates `summarizer.json`; the next `load_config()` hits
  `JSONDecodeError` and silently falls back to `{"enabled": False, ...}`, losing
  the user's backend/model/endpoint settings with no error surfaced.
