TokenTelemetry is **local-first** and binds to `127.0.0.1` by default. Remote access is opt-in and token-gated. Direct loopback requests (your browser on the same machine) are always exempt from the token requirement — the default local experience is unchanged. A request that reaches the backend through a reverse proxy is not a direct loopback request, even when the proxy runs on the same machine; see [Behind a reverse proxy](#behind-a-reverse-proxy).

<Callout type="warn">
**The token is the security boundary, not CORS.** CORS only restrains browsers; it doesn't stop direct HTTP clients (`curl`, scripts, other machines). Always use the token on any non-loopback bind. Only use `--insecure-no-auth` on a fully trusted private network.
</Callout>

## Direct access (tailnet, LAN, or VPS with open ports)

Use this pattern when you can reach the machine directly:

```bash
./start.sh \
  --host 0.0.0.0 \
  --allowed-origins your-laptop.tailnet.ts.net,192.168.1.42 \
  --port 13000 \
  --api-port 18000
```

### What happens

1. `--host 0.0.0.0` makes the backend listen on all interfaces (or use a specific IP like `--host 192.168.1.10`).
2. `--allowed-origins` sets the CORS allowlist for the backend and Next.js dev-server origins. Pass a comma-separated list of hostnames or IPs that will load the dashboard.
3. Because `--host` is non-loopback, **a random access token is auto-generated and printed once** in the terminal:
   ```
   ──────────────────────────────────────────────────────────
   Remote access is ON. Other devices must enter this token:

       abc123xyz...

   Or skip the typing — open this link (or scan its QR from the
   dashboard's "Connect a device" panel) on the other device:

       http://192.168.1.10:13000/?token=abc123xyz...

   The token is shown once — re-run to rotate it.
   ──────────────────────────────────────────────────────────
   ```
4. The dashboard shows a **"Connect a device"** panel with a QR code. Scan it on a phone or tablet to open the dashboard without typing the token.

### Using the token

Remote clients can authenticate in two ways:

- **Authorization header:** `Authorization: Bearer <token>` (for API clients). Works for every request.
- **URL parameter:** `?token=<token>` (for the initial browser load and for image/artifact links). The API accepts this form on `GET` and `HEAD` requests only; anything that changes state must send the header.

The frontend stores the token after the first load and strips it from the URL bar. Subsequent navigations within the same browser session are transparent.

A token in a URL is easier to leak than one in a header, so prefer the header in scripts. To limit the exposure of the URL form, the backend redacts `token=` values in its access log and, while a token is configured, sends `Referrer-Policy: no-referrer` on its responses so the URL is not passed on to other sites. Neither covers logs written by something in front of the backend: if you run a reverse proxy, redact the `token` query parameter in its access log too. If a token may have leaked, restart to rotate it (or pass a new `--auth-token`).

### Supplying a fixed token

To avoid rotating the token on every restart, supply one explicitly:

```bash
./start.sh --host 0.0.0.0 --auth-token mysecrettoken
```

Or via env var (flag wins over env):

```bash
TT_AUTH_TOKEN=mysecrettoken ./start.sh --host 0.0.0.0
```

### Concrete host shortcut

If you use a specific IP rather than `0.0.0.0`, you don't need to repeat it in `--allowed-origins`:

```bash
# --host 192.168.1.10 automatically adds 192.168.1.10 to the CORS allowlist:
./start.sh --host 192.168.1.10
```

With `0.0.0.0` (wildcard), Next.js can't derive a single hostname, so you still need `--allowed-origins`.

## Behind a reverse proxy

A reverse proxy on the same machine as the backend (`tailscale serve`, Caddy, nginx, …) connects to it from `127.0.0.1` on behalf of every remote user. To keep those users from inheriting the loopback exemption, the backend treats a loopback request as remote, and requires the token, whenever a token is configured and the request carries any of these headers:

`Forwarded`, `X-Forwarded-For`, `X-Real-IP`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `Via`

These headers are only ever used to withdraw the exemption. They never grant access, so sending them from a remote client achieves nothing.

What this means for you:

- **Your proxy must add at least one of those headers.** `tailscale serve` and Caddy's `reverse_proxy` send `X-Forwarded-For` by default. A bare nginx `proxy_pass` does **not**; add it explicitly:
  ```nginx
  location / {
      proxy_pass http://127.0.0.1:18000;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
  }
  ```
  A proxy that forwards without any of these headers is indistinguishable from a local browser, and its users will not be asked for the token.
- **Set a token even if the backend stays on loopback.** The launcher only generates a token for a non-loopback `--host`. If you keep the default bind and publish it through a proxy, export `TT_AUTH_TOKEN` yourself; without one the gate is off and the proxy is your only access control.
- **Through the proxy, everyone needs the token**, including a browser on the server itself, and the "Connect a device" panel is only available when the dashboard is opened directly on `localhost`.

Containers: with the provided `compose.yml` the backend sees the container network's gateway as the client address, not loopback, so once `TT_AUTH_TOKEN` is set every browser is prompted, local or not.

## SSH tunnel access (no port changes, VPS)

Use this pattern when:
- Your agents (and their logs) run on a remote VPS or server.
- You only have SSH access and don't want to open ports.
- You prefer to keep the dashboard bound to `localhost` on the remote side.

**On the remote machine** (where the agent logs live):

```bash
NEXT_PUBLIC_API_BASE=http://localhost:18000 ./start.sh
```

The `NEXT_PUBLIC_API_BASE` override tells the frontend to always talk to the backend at `localhost:18000` regardless of what address the browser opened the dashboard from.

**On your laptop:**

```bash
ssh -N -L 13000:127.0.0.1:13000 -L 18000:127.0.0.1:18000 user@remote-host
```

Then open **http://localhost:13000** on your laptop.

<Callout type="warn">
Forward **both** ports (`13000` and `18000`). A single-port forward (`-L 13000:...` only) shows a blank dashboard because the frontend tries to reach the backend at `localhost:18000` on your laptop instead of the remote machine.
</Callout>

This pattern requires no firewall changes and reuses your existing SSH authentication. No token is required because both services stay on loopback and the tunnel adds no forwarding headers.

## Disabling the token (trusted tailnet only)

If you're on a fully trusted private network (e.g. a Tailscale tailnet with device auth), you can disable the token entirely:

```bash
./start.sh --host 0.0.0.0 --insecure-no-auth
```

The launcher prints a prominent warning:

```
⚠  WARNING: --insecure-no-auth — the dashboard is exposed to the
   network with NO access token. Anyone who can reach this host can
   read your data and change settings. Only use this on a fully
   trusted private network (e.g. a tailnet).
```

Only use this if you understand the risk and have network-level access controls.

## Allowed origins configuration

`--allowed-origins` accepts a comma-separated list of values used in two places:

1. **Backend CORS** — origins allowed to make cross-origin requests to the API.
2. **Next.js dev server** — origins allowed to load the frontend chunks.

Each value is a **hostname or IP**, not a URL. A full origin is accepted and
reduced to its host, so `box.tailnet.ts.net`, `https://box.tailnet.ts.net` and
`https://box.tailnet.ts.net/` all mean the same thing. A listed host is allowed
on any port, including none: a deployment behind a proxy on `:443` or `:80`
sends an `Origin` header with no port at all, and that is allowed without you
having to write the port anywhere.

Loopback (`localhost`, `127.0.0.1`, `[::1]`) is always allowed on any port and
never needs to be listed.

For the QR / connect URL, the launcher picks a concrete reachable address using this preference order:

1. An explicit non-wildcard `--host` value.
2. The first `--allowed-origins` entry.
3. The primary non-internal IPv4 of the machine (autodetected).

If none of these yield a concrete address, the QR URL is omitted and you must type the token manually.

## Environment variable reference

| Variable | Equivalent flag | Notes |
| --- | --- | --- |
| `TT_AUTH_TOKEN` | `--auth-token` | Flag wins if both are set |
| `TT_ALLOWED_ORIGINS` | `--allowed-origins` | Set internally by the launcher; you can also export it |
| `TT_HOST` | `--host` | Passed to the backend |
| `TT_API_PORT` | `--api-port` | Passed to the backend |
