### Variant A — the double-counted cache tokens (real number, ready to post)

I opened a Copilot CLI session in my dashboard last week that claimed 63.2k input tokens. 62.9k of it was cache reads — counted twice.

Fixed in last week's release. If you track Copilot CLI usage, your input totals just got smaller — and honest.

## LinkedIn — cost-visibility post (longer version of the X insight)

**Three ways my own dashboard was lying to me — and what it took to notice.**

I build TokenTelemetry, a local dashboard that shows what AI coding agents actually cost. In the last two weeks, three separate accuracy bugs got fixed — each one a case where the numbers looked plausible and were wrong:

1. Cache-hit rate showed ~70%. The real rate was ~99.9%. The math divided a high-water mark by cumulative input, so the longer a session ran, the worse it looked. A community contributor (Tom Swift) caught it.

2. Everything past my 100 most recent sessions was frozen at zero tokens. A parse cap meant older history silently stopped counting — totals looked fine unless you knew what was missing. Another community contributor (Kyle Hutchinson) found and fixed it.

3. Copilot CLI input tokens were double-counted: a session reporting 63.2k input was really carrying 62.9k of cache reads stacked twice, inflating the cost estimate.

The pattern: cost dashboards fail quietly. Wrong numbers don't crash — they just sit there looking reasonable. The only defense I've found is verifying against the raw session logs, which is why the tool reads those logs directly instead of relying on an SDK reporting about itself.

If you're tracking agent spend — with any tool — spot-check one session against its raw transcript this week. It's 10 minutes and occasionally very informative.
